# 8. Extensions and plugins [normative]

- The extension exists to teach AT, and the first of them is the slang map: it is data that changes by region, by person and by time, and waiting for a release to be understood is too expensive.

- **There are two classes of plugin, and neither executes code in the engine.**
  - **Pure data**: a folder with a declaration and the data, with not one executable line. It has no runtime presence at all — it is not a process, not a reader: whoever reads the sentence is AT, and the plugin only says how to translate. That is why it does not ask for a read permission; asking would be theatre, and theatre teaches people to click "accept" without reading the next one.
  - **Declarative frontend**: a folder with `html` and `css`, **with no JS from the plugin**. The plugin describes the screen — the shell, the look, and the AT components it uses (`at-table`, `at-form`, `at-field`, `at-button`…) — and AT runs it. It runs in an iframe with `sandbox` and without `allow-same-origin` (an opaque origin, no session cookie, no access to AT's DOM). The server serves the plugin's files with a CSP that shuts the network and **every script that is not AT's component engine**: the plugin runs no code of its own and calls nothing. The plugin's HTML also goes through a sanitizer (no `<script>`, `on*=`, `javascript:` or external URL), which is defence in depth; containment is the `sandbox` plus the CSP.
  - **The design system is the plugin's vocabulary.** The iframe loads the design system's CSS and the person's active theme, so the plugin uses the published classes and components and inherits the look. What is published is a named, versioned subset, and the manifest declares the contract version it uses.
  - **Frontend with sandboxed JS** (future): when the vocabulary is not enough, a plugin will be able to bring `js`, in the same `sandbox`, talking to AT over a single `postMessage` channel. It does not exist yet.
  - **What stops it is the server.** The component engine and the bridge are a convenience; every installed plugin acts as an **actor** with its own role, generated from the manifest: the call the page makes on its behalf carries the plugin's credential, and the server applies the role, the risk ceiling and the audit as it does to any actor. What the manifest did not declare, the server refuses even if the bridge is bypassed.

- **The plugin carries a manifest**, and the manifest declares what it does in the environment. The permissions are granular and the person sees what they are installing. The first permission in AT's history is about what the plugin **alters**: *"Esse plugin pode alterar suas palavras antes de ser analisado pelo motor (core) do AT."* The sentence of the permission belongs to the **product**, rendered from the internal name in the product's `i18n` — the plugin merely references the id, because a warning written by whoever is being warned is not a warning. The plugin may add a note of authorship, marked as its own.

- **Installing ties a review to a hash.** AT sees what exists on disk and keeps the state; copying into the folder makes it **see**, and the act of installing is what counts. The plugin's whole folder is hashed, **content only, in canonical order** — no modification time, no permission, no empty folder —, and any altered byte changes the hash, invalidates the review and lowers the grade. The acceptances have to be made again, which closes the classic hole of trusting the author: the thing you approved and the thing that runs afterwards are the same, or AT knows they are not.

- The way back up the grade is an **explicit review**, in one of three modes: *I read what it does*, *I asked an AI to read what it does*, *I trust whoever made it*. Nobody verifies the declaration — it is the only possible format — and that is why the grade presents itself as a declaration (§3, The security posture).

- The plugin state lives in `app/`, in a file, and not in the tables. Since the folder is the person's, one can edit that state and lie to one's own grade: that is not a flaw in the design, because the hash protects you **from the author**, not the author from you.

- **Code in the engine stays out.** Code that executes on the server is hard to contain. The frontend plugin is accepted because it runs where the browser's containment reaches it — `sandbox`, CSP and a single bridge — and because the table-access request, declared in the manifest, is AT's **first data-access permission**: the person sees, table by table and action by action, what is being installed.

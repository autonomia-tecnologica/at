# 7. Container path: the steps [normative]

### Configuration steps

- The steps below are the container path. They are not a requirement for using AT: without them, what one has is the hosted path (§6), which is also supported. "Required" here means required for this path.

#### a. Create the container environment (required)

- This is the main switch of the environment. The person needs Podman installed. **`at-deploy`** checks whether it exists and, if it does not, offers the two ways out: install Podman, or continue on the hosted path. It does not install Podman on its own. From there on, **`at-deploy` orchestrates the environment and the services**, which come up as containers from pinned images.

- **The environment is a second artifact.** The whole of §7 — Podman, the VPN, the gate's containers, the edge's Caddy, the switch between the two paths and the only elevation in the product — lives in `at-deploy`, and `at-cli` keeps the folder and the app: it reads the same Working Folder and serves it with the deploy tool absent, refusing the Forms on the container path and closing when the gate falls. The boundary between the two is the folder's **state** and not an API — both read it, and the deploy tool is the one that writes the environment's (`App/services/`, the pins, the gate secret) — and the shared core (paths, `i18n`, files, the table engine) is one source and not two. It is why `at-cli` can promise, by what it is, that it never asks for administration permissions: the code that asks is not in it.

- It is a complex function with a lot of room for error and for a security failure. The security decisions around it are in [Security](rules.md#security).

- Podman is the choice for containers. The Caddy is the first service: the edge that publishes AT, now in a container, for the isolation.

- **The site is a NAME, and who resolves it is the private network — not a DNS of the environment.** The environment has no `dnsmasq` and no domain of its own (`at.local` died in TASK-187). With a private network up (§7e), the name is the one it gives the machine (`vpn.name`, today Tailscale's MagicDNS name, e.g. `host.example-tailnet.ts.net`), which the network's own agent already resolves for every device on it — the resolution the environment used to build for itself and no longer needs. With no private network at all, the name is `at.localhost`, which every browser resolves to the loop on its own, no DNS behind it. A name, and not the loop, because of two measurements: the gate refuses a cookie domain without a dot that is not an IP, and TLS needs a name to put in the SNI — a client connecting to an ADDRESS sends none, and the edge answers the handshake with an error because it has no certificate it can serve.

- **Notification has no name of its own and no port of its own.** It is the PWA's Web Push (§7f): the person opens the SAME `https://<name>` as the site and turns notifications on there, and the browser's own push service is what delivers. There is no second name to resolve and no second port to separate them — the provider's access rule names the site, and that is the only one there is.

- **The valid certificate is not AT's: it comes from `tailscale serve`, on the person's machine.** AT installs no CA at all and no longer has a certificate-delivery flow (the `at-deploy ca install` word died with `cert.at.local`, and with it `at_deploy/trust.py`). The Caddy stays on `tls internal` — it is the edge that serves the name —, and on top of it the person runs `tailscale serve`, a feature of Tailscale itself that issues a valid Let's Encrypt certificate for the machine's MagicDNS name and proxies to the Caddy. `at-deploy` **never manages the VPN**: it only READS the address and the name (`ip -4`, `status --json`, §7e), and whoever brings up `tailscale serve` is the person.

- **The container does not read the folder: it reads a run directory outside it.** `up` materializes what each service reads into a run directory — the user's run directory on the machine when it exists, the system's temporary one when it does not —, **outside the Working Folder**, and every service's `--volume` points there. **The state folder keeps being the source**: the run directory is the copy that serves the boot, and it dies with the environment — `down` removes it —, because what the folder keeps is what the backup carries. Its name carries the folder's id, and never its name: two environments on one machine do not cross, and nobody's folder name shows up in a shared directory. **What the container FILLS does not leave the folder**: the provider's `data` and the Caddy's `storage`, where the CA and the certificates live, stay inside it, which is the one that outlives the container. **And AT does not repair the folder**: a state path with the wrong shape — a file where the service mounts a folder, a folder where AT writes a file — is a **spoken REFUSAL**, with the path and what it should be, and never a silent repair; the path may be the person's, and AT does not touch what is not its own. The check comes before the Main Key and before the elevation, because a boot that cannot succeed does not get to ask for anything.

- **It is this road that answers how a sealed file is read back without the Main Key in the process (§4).** Whoever opens the envelope is `up`, once, with the Main Key typed at boot, and what the container mounts is the clear copy. The readers of the container path are three, and each receives what it needs from a named place: **the Caddy**, which reads the `Caddyfile` — and the gate secret inside it — in the copy of its own service; **the provider**, which reads the `configuration.yml` and the three secrets it carries in its own copy, and which writes its notifications into a FILE of the state folder, where they outlive the container; and **the WebApp**, which reaches the gate secret through the whole-folder mount it already has (§7c) — and that mount is the folder's —, receiving the clear copy of the gate in a mount of its own because of that, with the environment saying where it is. **No process inside the container opens the vault**: whoever opens it is whoever brings the environment up.

- **What AT DRAWS goes sealed by the Main Key, and the container reads the open copy.** `up` asks for the Main Key once — §4: typing it when AT comes up is grade `S` —, and it is what seals the values the environment draws: the gate secret, **the Caddy's own**, embedded in the Caddyfile it reads out of the run directory; and the provider's three (`session`, `encryption` and `jwt`), which are its own. **The scope of the derived key is the name of the service that owns the value** (§4: one per service or purpose), and it comes from the Main Key and from nothing else, at every boot. The folder keeps the ENVELOPE and the run directory receives the OPEN value: neither the `Caddyfile`, nor the `configuration.yml`, nor any file of the folder is read without the Main Key. **Without it the environment does not come up, and says why**: with no terminal nothing is asked, and a Main Key that does not open what the folder keeps mounts nothing — what was not opened is not used. **The Main Key is asked when there is something to open, to seal or to migrate**, and a folder born before the seal — the values AT draws written **in the clear**, and no envelope — is **MIGRATED** on the first boot after the swap: `up` asks for it, **re-draws** every clear value and seals it. Sealing without rotating would not be enough: the folder's `.gitignore` keeps the values out of git, but it does not stop a copy, and a value that was once on disk does not become a secret again by being sealed later — whoever holds an old copy is left with a dead value, which is what the rotation buys. **The price of the rotation, said out loud**: making the provider's `encryption` another one makes **ILLEGIBLE** everything it has already encrypted; `session` takes the open sessions down; `jwt` invalidates the tokens already issued; and the new gate only holds once the Caddy and the WebApp come up together with it — which the boot itself does. **And the provider's restart asks for it too** (`at-deploy credential`), because it rewrites the `configuration.yml` and mounts the run directory again.

- **What the container FILLS stays OUT of the vault's reach, and that is a decision with a declared price.** The Caddy's `storage` — the local CA and the certificates issued against it, with each one's private key — is not drawn by AT: what writes it is the Caddy itself, while it is up, on its own renewal cadence, and no boot passes through there to seal it. And the Main Key does not get inside it: this section says that no process inside the container opens the vault, and a key the Caddy would need to encrypt what it writes itself would be ITS OWN and would live beside what it encrypts — in the folder the copy carries —, and that buys nothing. With no seal that reaches it, this object **is not sealed: it is declared**. **The price, said out loud**: a copy of the folder carries the CA's private key, and with it anyone issues a certificate that AT trusts — the backup's promise bought backwards. **The same holds for the other folders the container fills** — the provider's `data` —, and for the same reason. What AT does with what it did not write is what the folder already promised: it does not write, does not seal, does not move, and does not take it out of the state folder.

#### b. Install the identity provider as a container (required)

- AT has an authenticator of its own, and on the container path it is the gate: an external identity provider, here Authelia, in front of everything. It becomes responsible for the authentication of all the services existing here, and AT comes in as one more app — not as an exception.

- Authelia speaks **OIDC** with whoever speaks OIDC, and **forward-auth** with whoever does not. Sonarr, Radarr and Prowlarr do not speak OIDC, and it is forward-auth that gives them the same experience: one login at the portal, the cookie holding for all. AT does not speak OIDC with it either: it comes in through forward-auth, like the others.

- The split is: **who** is an actor belongs to AT, and **how** it is proved that it is them belongs to Authelia. The `actor` table (§4) holds identity, role and the hashed credential — and on the container path whoever uses the Authelia credential is Authelia.

- What Authelia **is not**: a login provider with Google. It does not play the relying party role, and that is a decision of the project, not configuration. Login with third parties is not part of AT.

- Here there is no authentication with AT's face. The portal is Authelia's, and what AT does is ask it to be as neutral as possible, so as not to look like what it is not (§5).

- What AT demands from whoever arrives with an identity is the **gate secret**: a value drawn by `at-deploy` at installation, written into the Caddyfile it generates itself, attached by Caddy to every request carrying an identity, and refused to whoever does not bring it. It is the M2M between Caddy and AT's WebApp, and Authelia never sees it. The file is the folder's state, so `at` reads it too — on the container path it is what makes an identity an identity, and the deploy tool is only what drew it.

- **The folder's own people are what the gate proves, and `at-deploy` is the door that keeps them.** Who is an actor belongs to AT (§4) and how it is proved belongs to Authelia, so changing a credential is one act over both: `at-deploy credential <name>` writes the credential into the actor's row — hashed, as the Forms and Basic already prove it — derives the `users.yml` from that same row, and brings the provider up again, because Authelia reads that file at START and a derivation rewritten under a standing container is a derivation nothing proves. A person with no credential is not in the file, and giving them the first one is the same act.

- **Who is logged in is the provider's own MEMORY, and that is the declared price.** The session secret is drawn once and kept in the folder, and it is what seals the cookie: the same value across a restart keeps the cookie SIGNED — but whoever it names does not cross with it, because the provider keeps that registry nowhere outside its own container. A restart of the provider — a changed credential, an `at-deploy update`, a crash, a stray `podman restart` — zeroes the memory and sends the person back to login with a cookie the new provider no longer knows. The way to end every session on purpose is the same as always: a new session secret.

#### c. Install the WebApp as a container (required)

- The WebApp, the main way of using AT, is installed as a container. It aims to reduce the blast radius in a compromised web application.

- **The WebApp answers on the container's network, and the edge reaches it by name.** This is measured and not a preference: an app listening on its own container's loop is reached by nobody — the published port lands on the container's network address and finds nothing there, and the edge is another container, whose `127.0.0.1` is itself. So the app listens on the container's addresses, and what keeps that from being an exposure is the gate secret (§7b): whoever reaches it and brings no secret is refused with `403`.

- **The environment's network is one, and what decides a service's place in it is who it has to talk to.** A container's `127.0.0.1` is itself and nobody else, and two networks do not reach each other at all — measured, no route and no name — so the Caddy (which proxies to the WebApp and asks the gate about every request), the WebApp (which asks the gate whether its portal is standing) and the gate stand together.

- **The WebApp's port is the one AT serves by default, and it is not published.** Exposing moves the address the person reaches, never the one the WebApp listens on — and who reaches it is the edge, on the network the two share, or nobody at all.

#### d. Install the spelling and grammar checker as a container (optional)

- AT's default for text correction is LanguageTool, today the tool that fulfils the `spelling-checker` service (§4). It serves to underline errors on the editing screen. Quite useful.

- This is the checker of the **person's text**, at run time. The checker of the repository's documents is another one, and it is a development tool ([derivation §3](derivation.md)).

#### e. Install a VPN (optional)

- AT allows configuring a VPN. Here it is relevant, because it allows creating a private network so that multiple devices talk to each other. So if the AT WebApp runs on your personal machine, it becomes securely reachable from your phone, anywhere. Here I am using Tailscale. It is proprietary, but it avoids needing a server in the cloud. Headscale support in the future.

#### f. Notification: the PWA's Web Push (no container)

- **The notifier is not a service of the environment: it is the PWA's own Web Push.** AT's notification is the browser's — the PWA's service worker subscribes to the *push service* (FCM on Chrome/Android, Mozilla on Firefox), and the operating system draws the alert. There is no container to install, no account to create, no topic to configure and no second port to separate.

- **Whoever fulfils the `notifier` service (§4) is `at/core/push.py`**, inside the `at-cli` that serves the WebApp, on BOTH paths. It draws the **VAPID** pair (P-256) in the folder — `App/services/push/` —, keeps the subscriptions the browsers send, and encrypts each alert with `aes128gcm` (RFC 8291) and the `ES256` JWT (RFC 8292) on delivery to the push service. The private half never leaves the folder; only the PUBLIC key travels to the page.

- **The page never holds a secret.** To subscribe it asks for the public key (`/api/push/key`) and returns the subscription (`/api/push/subscribe`); the alerts it lists come from inside, from the route `notifier:read` covers (§4), and never from a credential the browser keeps.

- **The phone reaches no port beyond `443`.** It opens the same `https://<name>` as the site, installs the PWA and turns notifications on in Settings; from then on the one talking to it is the browser's own push service. The only port leaving the machine is the site's.

- **Delivery is best-effort.** An alert that did not go out is not an exception the clock's round has to survive by name; a subscription the push service retired (`404`/`410`) is dropped rather than insisted on, and the alert repeats on the next pass.

- This is where the first graded functionality comes in: its levels and what each one costs live in [functionalities](functionalities.md).

# 7. Container path: the steps [normative]

### Configuration steps

- The steps below are the container path. They are not a requirement for using AT: without them, what one has is the hosted path (§6), which is also supported. "Required" here means required for this path.

#### a. Create the container environment (required)

- This is the main switch of the environment. The person needs Podman installed. **`at-deploy`** checks whether it exists and, if it does not, offers the two ways out: install Podman, or continue on the hosted path. It does not install Podman on its own. From there on, **`at-deploy` orchestrates the environment and the services**, which come up as containers from pinned images.

- **The environment is a second artifact.** The whole of §7 — Podman, the VPN, the DNS, the gate's containers, the edge's Caddy, the switch between the two paths and the only elevation in the product — lives in `at-deploy`, and `at-cli` keeps the folder and the app: it reads the same Working Folder and serves it with the deploy tool absent, refusing the Forms on the container path and closing when the gate falls. The boundary between the two is the folder's **state** and not an API — both read it, and the deploy tool is the one that writes the environment's (`App/services/`, the pins, the gate secret) — and the shared core (paths, `i18n`, files, the table engine) is one source and not two. It is why `at-cli` can promise, by what it is, that it never asks for administration permissions: the code that asks is not in it.

- It is a complex function with a lot of room for error and for a security failure. The security decisions around it are in [Security](rules.md#security).

- Podman is the choice for containers. `dnsmasq` and Caddy are the first services. The first to customize the access urls and the second to publish AT, now in a container, for the isolation.

- **The site is a NAME, and the DNS of the environment is what answers for it.** `at.local` is the environment's domain, and the services that are reached by a name hang theirs under it: the AT site keeps `at.local` itself, and the notifier of §7f answers at `ntfy.at.local`. A subdomain and not a path of the site's, because it was measured: the notifier's own clients do not work under a path. **And AT's CA answers at `cert.at.local`**, the third name and the only one with no service behind it: what answers it is the edge itself, serving out of a file the `root.crt` it issued, because whoever has to trust the certificate is a device that does not read the machine's disk — it reads a URL — and until then has no way to fetch it. **It stands outside the gate**, and by the same measurement that took the notifier out from behind it: whoever arrives there does not trust the certificate yet, and a question answered by redirect would be answered by the very certificate the CA would have to sign. The first visit still asks for the click-through, and that is inherent: it is TLS without a trusted CA. `dnsmasq` answers all three with the address the edge is actually at — the private network's when there is one (§7e), the loop when there is not — so the network decides WHERE, and never what the names are. A name, and not the loop, because of two measurements: the gate refuses a cookie domain without a dot that is not an IP, and TLS needs a name to put in the SNI — a client connecting to an ADDRESS sends none, and the edge answers the handshake with an error because it has no certificate it can serve. What the person types is the name, so the machine has to use that DNS. **And `dnsmasq` is published where the edge is** — the private network's address when there is one, the loop when there is not (§7e) — and not on the loop alone: whoever resolves the names from outside the machine, another device's browser or the phone, cannot ask a service that only answers inside it. That address is the one the private network's DNS is pointed at.

- **AT's CA goes to the store of the browser ON this machine through a word of `at-deploy`.** `cert.at.local` solves the device that does not read this machine's disk — the phone, another computer's browser —, and the local browser is another problem: Firefox does not read the system store, it has its own NSS, one per profile (`cert9.db` inside each), and Chromium reads `~/.pki/nssdb`. What writes to both databases is `certutil`, which comes from the `nss` package, and that is what the word uses: **`at-deploy ca install [<target>]`** puts the CA in both stores that exist, and naming the target — `firefox` or `chromium` — narrows the act. **`at-deploy ca uninstall`** takes it back out by the same nickname, because a store that only grows is a store nobody audits. Both databases are the person's OWN files, so the word asks for no elevation at all: **the system store stays out**, and not by oversight — it would be the second entry in §3's closed list, and Firefox does not read it anyway. With no `certutil` on the machine, `at-deploy` installs nothing: it says the two ways out — install the package and run again, or import the CA by hand from the certificate screen, since it is within reach by name —, the same shape Podman follows. The browser's first visit still asks for the click-through, and that is inherent to having no public CA; what the word delivers is the warning going away after that, with no cable and no `scp`.

- **The container does not read the folder: it reads a run directory outside it.** `up` materializes what each service reads into a run directory — the user's run directory on the machine when it exists, the system's temporary one when it does not —, **outside the Working Folder**, and every service's `--volume` points there. **The state folder keeps being the source**: the run directory is the copy that serves the boot, and it dies with the environment — `down` removes it —, because what the folder keeps is what the backup carries. Its name carries the folder's id, and never its name: two environments on one machine do not cross, and nobody's folder name shows up in a shared directory. **What the container FILLS does not leave the folder**: the provider's and the notifier's `data` and the Caddy's `storage`, where the CA and the certificates live, stay inside it, which is the one that outlives the container. **And AT does not repair the folder**: a state path with the wrong shape — a file where the service mounts a folder, a folder where AT writes a file — is a **spoken REFUSAL**, with the path and what it should be, and never a silent repair; the path may be the person's, and AT does not touch what is not its own. The check comes before the Main Key and before the elevation, because a boot that cannot succeed does not get to ask for anything.

- **It is this road that answers how a sealed file is read back without the Main Key in the process (§4).** Whoever opens the envelope is `up`, once, with the Main Key typed at boot, and what the container mounts is the clear copy. The readers of the container path are three, and each receives what it needs from a named place: **the Caddy**, which reads the `Caddyfile` — and the gate secret inside it — in the copy of its own service; **the provider**, which reads the `configuration.yml` and the three secrets it carries in its own copy, and which writes its notifications into a FILE of the state folder, where they outlive the container; and **the WebApp**, which reaches the gate secret through the whole-folder mount it already has (§7c) — and that mount is the folder's —, receiving the clear copy of the gate in a mount of its own because of that, with the environment saying where it is. **No process inside the container opens the vault**: whoever opens it is whoever brings the environment up.

- **What AT DRAWS goes sealed by the Main Key, and the container reads the open copy.** `up` asks for the Main Key once — §4: typing it when AT comes up is grade `S` —, and it is what seals the values the environment draws: the gate secret and the notifier's M2M credential, **both the Caddy's own** and both embedded in the Caddyfile it reads out of the run directory; the provider's three (`session`, `encryption` and `jwt`), which are its own; and **AT's own credential in the notifier**, which is read from OUTSIDE the container and therefore never goes through the run directory at all. **The scope of the derived key is the name of the service that owns the value** (§4: one per service or purpose), and it comes from the Main Key and from nothing else, at every boot. The folder keeps the ENVELOPE and the run directory receives the OPEN value: neither the `Caddyfile`, nor the `configuration.yml`, nor any file of the folder is read without the Main Key. **Without it the environment does not come up, and says why**: with no terminal nothing is asked, and a Main Key that does not open what the folder keeps mounts nothing — what was not opened is not used. **The Main Key is asked when there is something to open, to seal or to migrate**, and a folder born before the seal — the values AT draws written **in the clear**, and no envelope — is **MIGRATED** on the first boot after the swap: `up` asks for it, **re-draws** every clear value and seals it. Sealing without rotating would not be enough: the folder's `.gitignore` keeps the values out of git, but it does not stop a copy, and a value that was once on disk does not become a secret again by being sealed later — whoever holds an old copy is left with a dead value, which is what the rotation buys. **The price of the rotation, said out loud**: making the provider's `encryption` another one makes **ILLEGIBLE** everything it has already encrypted; `session` takes the open sessions down; `jwt` invalidates the tokens already issued; and the new gate only holds once the Caddy and the WebApp come up together with it — which the boot itself does. **And the provider's restart asks for it too** (`at-deploy credential`), because it rewrites the `configuration.yml` and mounts the run directory again. **And AT's own manual delivery asks for it in its own act** (`at-deploy notify`): it shares no derived key with `up`, so opening the notifier's token asks for the Main Key again — and that is the delivery's declared price: **without the Main Key the alert does not go out**, and an alert that does not go out is an alert that does not go out (§7f, the best-effort part).

- **What the container FILLS stays OUT of the vault's reach, and that is a decision with a declared price.** The Caddy's `storage` — the local CA and the certificates issued against it, with each one's private key — is not drawn by AT: what writes it is the Caddy itself, while it is up, on its own renewal cadence, and no boot passes through there to seal it. And the Main Key does not get inside it: this section says that no process inside the container opens the vault, and a key the Caddy would need to encrypt what it writes itself would be ITS OWN and would live beside what it encrypts — in the folder the copy carries —, and that buys nothing. With no seal that reaches it, this object **is not sealed: it is declared**. **The price, said out loud**: a copy of the folder carries the CA's private key, and with it anyone issues a certificate that AT and the phone trust — the backup's promise bought backwards. **The same holds for the other folders the container fills** — the provider's `data` and the notifier's —, and for the same reason. What AT does with what it did not write is what the folder already promised: it does not write, does not seal, does not move, and does not take it out of the state folder. **The one file it reads there is `root.crt`** (`authority_file`), which is the PUBLIC half of the CA and what the person imports into the browser and the phone's app; the private keys beside it, AT does not read.

#### b. Install the identity provider as a container (required)

- AT has an authenticator of its own, and on the container path it is the gate: an external identity provider, here Authelia, in front of everything. It becomes responsible for the authentication of all the services existing here, and AT comes in as one more app — not as an exception.

- Authelia speaks **OIDC** with whoever speaks OIDC, and **forward-auth** with whoever does not. Sonarr, Radarr and Prowlarr do not speak OIDC, and it is forward-auth that gives them the same experience: one login at the portal, the cookie holding for all. AT does not speak OIDC with it either: it comes in through forward-auth, like the others.

- The split is: **who** is an actor belongs to AT, and **how** it is proved that it is them belongs to Authelia. The `actor` table (§4) holds identity, role and the hashed credential — and on the container path whoever uses the Authelia credential is Authelia.

- What Authelia **is not**: a login provider with Google. It does not play the relying party role, and that is a decision of the project, not configuration. Login with third parties is not part of AT.

- Here there is no authentication with AT's face. The portal is Authelia's, and what AT does is ask it to be as neutral as possible, so as not to look like what it is not (§5).

- What AT demands from whoever arrives with an identity is the **gate secret**: a value drawn by `at-deploy` at installation, written into the Caddyfile it generates itself, attached by Caddy to every request carrying an identity, and refused to whoever does not bring it. It is the M2M between Caddy and AT's WebApp, and Authelia never sees it. The file is the folder's state, so `at` reads it too — on the container path it is what makes an identity an identity, and the deploy tool is only what drew it.

- **The folder's own people are what the gate proves, and `at-deploy` is the door that keeps them.** Who is an actor belongs to AT (§4) and how it is proved belongs to Authelia, so changing a credential is one act over both: `at-deploy credential <name>` writes the credential into the actor's row — hashed, as the Forms and Basic already prove it — derives the `users.yml` from that same row, and brings the provider up again, because Authelia reads that file at START and a derivation rewritten under a standing container is a derivation nothing proves. A person with no credential is not in the file, and giving them the first one is the same act.

- **The restart does not evict whoever is already inside, and that price is declared.** The session secret is drawn once and kept in the folder, and it is what seals the session cookie: the same value across a restart keeps every session that was open. **And the registry those sessions live in is not the provider's memory**: it is `redis`, a service of the environment with a container of its own, which comes up right after the DNS and before the provider — a gate that stands with the registry behind it has nowhere to keep who is inside. It is what makes a restart of the provider ALONE — a crash, a healthcheck, a stray `podman restart` — leave the people inside where they were. **What it carries is volatile and it keeps nothing on disk**: the RDB and the AOF are off, no volume exists to persist session content, and the price is said — a restart of the Redis itself takes the registry, and the open sessions with it. **And an `at-deploy update` recreates every container, the Redis included**, so it does drop the sessions: what the service answers for is the provider restarting on its own, and not an update of the whole infrastructure. So a credential changed because it leaked leaves the sessions it had opened standing until they expire — and the way to end them is a new session secret, which ends every session in the folder with it.

#### c. Install the WebApp as a container (required)

- The WebApp, the main way of using AT, is installed as a container. It aims to reduce the blast radius in a compromised web application.

- **The WebApp answers on the container's network, and the edge reaches it by name.** This is measured and not a preference: an app listening on its own container's loop is reached by nobody — the published port lands on the container's network address and finds nothing there, and the edge is another container, whose `127.0.0.1` is itself. So the app listens on the container's addresses, and what keeps that from being an exposure is the gate secret (§7b): whoever reaches it and brings no secret is refused with `403`.

- **The environment's network is one, and what decides a service's place in it is who it has to talk to.** A container's `127.0.0.1` is itself and nobody else, and two networks do not reach each other at all — measured, no route and no name — so the Caddy (which proxies to the WebApp and asks the gate about every request), the WebApp (which asks the gate whether its portal is standing) and the gate stand together. The DNS is the one service that talks to nobody, and it is the one service on the environment's DMZ, where it cannot reach the WebApp.

- **The WebApp's port is the one AT serves by default, and it is not published.** Exposing moves the address the person reaches, never the one the WebApp listens on — and who reaches it is the edge, on the network the two share, or nobody at all.

#### d. Install the spelling and grammar checker as a container (optional)

- AT's default for text correction is LanguageTool, today the tool that fulfils the `spelling-checker` service (§4). It serves to underline errors on the editing screen. Quite useful.

- This is the checker of the **person's text**, at run time. The checker of the repository's documents is another one, and it is a development tool ([derivation §3](derivation.md)).

#### e. Install a VPN (optional)

- AT allows configuring a VPN. Here it is relevant, because it allows creating a private network so that multiple devices talk to each other. So if the AT WebApp runs on your personal machine, it becomes securely reachable from your phone, anywhere. Here I am using Tailscale. It is proprietary, but it avoids needing a server in the cloud. Headscale support in the future.

#### f. Install the notifier as a container (optional)

- With everything configured, the cherry on the cake is `ntfy`, today the tool that fulfils the `notifier` service (§4). The configured reminders can be notified directly as a Push Notification, and it is through it that the approval of a demand that passed the risk threshold arrives.

- **The notifier now stands behind the SAME gate as the site**, and that reverses the earlier measurement without repeating its mistake. The gate authenticates by redirect and by session cookie, so a headless phone app used to take the 302 and never connect — measured, `subscribers=0` behind Authelia and `101` without it. **Authelia's forward-auth reads an `Authorization: Basic` header on the request itself and authenticates it directly, with no redirect, whenever one is there** — and the ntfy app's own login always sends one, so the client that broke against the redirect never takes it in the first place. The identity provider's access rule names `ntfy.at.local` beside the site's own domain, with the same `one_factor` policy: the SAME Chave Principal that proves a person at `at.local` proves them at `ntfy.at.local` too — no credential of the notifier's own for a person to hold. The decision is recorded in [Security](rules.md#security).

- **Past the ask, the edge talks to the notifier DIRECTLY — never through the WebApp — and swaps the `Authorization` it received for AT's own.** The Caddyfile's second site reverse-proxies straight to the notifier's container, with a `header_up Authorization "Basic <value>"` that overwrites whatever the client sent: the notifier never sees the person's credential, only the M2M's. This is the same shape the gate secret already uses to tell the WebApp a request came through the edge (§7b) — a header the edge attaches, not a value the client controls.

- **AT talks to the notifier with ONE account now, and it is `read-write`.** The scope §3 asks of whoever reaches AT applies here in its mirrored form: with `ntfy access at at read-write`, the account answers `200` on the topic `at` and `403` on any other. It is the one account both the edge's swapped `Authorization` and AT's own reminder delivery authenticate as — there is no second, narrower account for a phone any more, because the edge is what decides who reaches the topic at all now.

- **The M2M value Caddy attaches is drawn BEFORE any container exists — the same moment as the gate's own secret — because nothing else works.** The manifest starts Caddy before the notifier (§7f is the LAST service), so the Caddyfile is written and the edge is up long before ntfy could hand back a token of its own. AT draws a password itself instead, seals it in the shape the `Authorization: Basic` header needs, and embeds it in the Caddyfile the same way the gate secret is embedded — the state folder keeps the envelope, and the run directory the container reads gets the opened value. **When the notifier's OWN container finally stands**, AT recovers that same password from the very value it already sealed and creates the account with it — one value, drawn once, and the two sides agree by construction rather than by a second exchange.

- **AT's own delivery keeps its separate token**, drawn by the notifier itself inside its container (`ntfy token add`) — kept in a `0600` file beside the state of that service, **sealed by the Main Key** (item 50), read only by `at-deploy notify`'s own POST to the loop. Nothing about the reminder's own road changed: it still depends on nothing but the notifier's container being up, not on the edge, the DNS or a certificate.

- **The phone reaches the notifier by its NAME, and the certificate is AT's own — imported into the APP, not into the device.** The road is `https://ntfy.at.local`, on `443`, with the certificate the edge issues per name (`tls internal`), and it is the same port as always: never another one. **Measured, and it is what decides the shape:** AT's certificate comes from a local CA, and a modern Android app **ignores the CA the person installed in the system** — the one that trusts is the app, and the ntfy app has certificate management of its own, with a self-signed certificate supported since v1.22.1. So what the person does on the device is import **AT's CA** — the `root.crt` the edge keeps inside the Caddy's state folder — into the app's own certificate management, and not into the system store. The same goes for the name: the device has to resolve `ntfy.at.local` on the environment's DNS (§7a).

- **The raw port a phone once reached directly is gone.** Before the edge fronted the notifier, its port had to leave the loop too, so a device on the private network could reach it without a name; now that every outside road goes through the edge on `443`, that second door would only be one more way past the ACL with no Chave Principal behind it at all. The port stays on the loop, always — the same address AT's own delivery already used, and the one no device but this machine can reach.

- This is where the first graded functionality comes in: its levels and what each one costs live in [functionalities](functionalities.md).
